Q-001 BLOCKING Blocks: TASK-0A-003

Guest account data on upgrade

Question. What should happen to anonymous guest data when the user later signs into an email account?

Why it matters. Auth.tsx offers signIn("anonymous") with no claim path. A guest who later signs in by email receives a different user id, so every task, expense and note is silently orphaned. This is defect N2 and it violates the "no silent data loss" principle. It is an account-model decision, not a UI bug.

OptionWhat it meansConsequence
A — MigrateMove anonymous data into the authenticated account on first sign-in.Best for users. Needs a marker column on users or an auth hook; a data-window policy must be chosen.
B — RemoveDrop anonymous sign-in entirely.Simplest and safest. Loses a conversion/demo affordance.
C — OtherAnother explicitly approved approach.—

Info needed to decide: (1) Is guest sign-in a conversion tool or a demo affordance? (2) Is there an acceptable migration window — drop data older than N days? (3) Does Convex Auth expose a hook to claim an anonymous identity, or does Panel need its own marker column?

Product

Source: 03_PRODUCT_CONTEXT.md

Thesis

Most dashboards die because they are organisational tools pretending to be operational tools. Panel wins by never asking the user to maintain a second system — it derives its value from data their existing tools already generate, and spends that value on one thing only: telling the person what to do next.

What it is

  • A personal operating layer
  • Answers "what needs attention right now?"
  • Sits above Gmail, Calendar, banking, health, Notion
  • Learns from your own completions, and says why

What it is not

  • Not another Notion / Asana / Jira
  • Not a banking app or fitness tracker
  • Not a CRM, chatbot or Zapier
  • Not a blank-canvas dashboard
  • Not an AI wrapper

Segments

  • Overloaded individual — primary
  • Self-employed / freelancer — primary
  • Family co-ordinator — secondary
  • Privacy-sensitive pro — secondary

Competitive landscape — what to learn, what not to copy

CategoryPanel should learnPanel must NOT copy
Task managers
Todoist, Things, TickTick		 Capture quality is the front door; their parsing is the benchmark. Not a place to plan. Panel wants to know what is.
Dashboards
Glance, Heimdall, Homer		 Glance has no task management — because tasks need entry. Integrations must feed tasks. The configurable widget grid. That is the blank-canvas dashboard.
Finance
YNAB, Monarch, Lunch Money		 Bank connection UX and transaction hygiene. A double-entry ledger. Also: confident financial advice.
Family
FamFam, shared sheets		 Sharing must be simple and legible. Nobody wants to manage ACLs. A purpose-built family app bolted alongside a personal one.
Personal CRM
Dex, Monica, Clay		 What a useful person profile contains: dates, cadence, what is owed each way. Salesforce. Panel is not for tracking strangers.
Automation
Zapier, Make, IFTTT		 Reliable normalisation and idempotent re-runs (ADR-012). A trigger builder, workflow canvas, or plugin marketplace.
Health
Whoop, Oura, Fitbit		 Passive-by-default beats active-by-default. This is the model. Building sensors. Consume health context; do not manufacture it.
Knowledge
Notion, Obsidian		 Nothing about structure. Only what makes a database feel fast. Any of it. MAIN_AGENT names Notion first.
Calendar AI
Reclaim, Clockwise		 "Defend time for tasks" is a strong candidate attention rule. Auto-writing to the user's calendar. That is a confirm action.

Strategic read: every category knows one domain well and is blind to the relationships between domains. The value is in the relationships — and relationships only exist where several kinds are held at once.

Research honesty

There is no primary research with Panel users. No interviews, no usability testing, no cohort or conversion data. Every product belief is inherited from adjacent categories or is our own reasoning.

Phase 3 should not begin before real user contact, because by then the cost of being wrong compounds.

Metrics reality

No analytics, no telemetry, no event pipeline. Most defined metrics are therefore not currently measurable.

North star: Weekly Useful Attention — attention items per week the user actually acts on.

Guard metric: Trust & privacy incidents — any non-zero value is a stop-the-line event.

Agent Authority

Source: 01_MAIN_AGENT.md §9

The governing rule

The development agent may modify implementation artifacts. The development agent may NOT modify product decisions, ADR decisions, security invariants, or phase approval state merely to make implementation easier.

If a task cannot proceed without one of those, that is an Open Question — not an obstacle to route around.

Hardened the spec system into an operating system

Why: the first pass documented Panel. It did not yet govern it. Clamp ±3.0 · lr decays by samples · min 12 samples to rank · min 5 to train dismissal · ≥1 exploration slot per section · snapshots + rollback + reset.

Agents — three tiers

  • automatic — safe internal ops only
  • proposed — user accepts, never auto-executes
  • confirm — money, sending, sharing, deletion, tax filing

Idempotency keys are deterministic hashes. Never mutate user data without acceptance.

Security model

  • Ownership ≠ access; sharing never changes owner
  • Many-to-many space membership
  • Grants fail closed; deny by default
  • Credentials server-only, internal functions only
  • Private data is not stored

Integrations

  • One adapter → one NormalizedBatch → one writer
  • Idempotent on (provider, externalId)
  • Calendar inbound only, calendar.readonly
  • Private events stored as the literal "Busy"

Non-negotiable rules (abridged — full list in SYSTEM_FUNDAMENTALS §10)

  1. Typed entity tables. No generic object table. No EAV.
  2. links holds relationships only, from a closed vocabulary.
  3. Ownership separate from access; membership many-to-many.
  4. Deny by default.
  5. Hard rules bypass learned ranking entirely.
  6. No learning from absence. Snooze is not negative feedback.
  7. No learned category suppression.
  8. Agent idempotency mandatory; risky actions require confirmation.
  9. Credentials server-only; minimum OAuth scope.
  10. No external LLM API. Ever.
  11. No speculative frameworks. Attention is computed, not stored.
  12. Markdown is the specification; testing is a gate.
